- 2026-08-18 — Daily FX refresh is a QStash cron (`/api/cron/fx`, `QSTASH_FX_CRON`, default `0 11 * * *`) pulling USD/EUR/GBP CAD pairs from the Bank of Canada Valet API in one multi-series request. Registered in `scripts/qstash-schedules.mjs` like the other jobs; run `npm run qstash:schedules` to create it. An empty fetch returns 502 and leaves existing rates untouched — without a rate on file foreign spend cannot accrue at all, so a silent 200 would hide a real gap. Rates are written per user because `FxRate` is per-user by design (a user may hold manual rates). JMD has no Bank of Canada pair, so JMD spend still cannot accrue.

- 2026-08-18 — Foreign spend now ACCRUES into the CAD cap ledger via the user's own stored `FxRate` rows, instead of being dropped. Dropping it under-counted caps, so the engine could recommend a card nearer exhaustion than the ledger believed; converting without a rate would be the opposite sin, so a missing rate still fails closed and is logged (`[cap-usage] no accrual … missing-fx-rate`) rather than passing silently. Each `CapAccrual` now stores `sourceAmountMinor`/`sourceCurrency`/`fxRate`/`fxRateAsOf` so a figure can be audited without re-deriving which rate was live. `Scorer.fallbackCadToUsd = 0.73` is untouched — it is card-contract behaviour gated by the 27 golden fixtures in both languages, not an FX policy.

- 2026-08-17 — Statement matching runs an ordered pass table (exact → tip-tolerant → pre-auth hold), each pass sweeping the whole upload before the next starts. The pre-auth pass claims lines where the candidate is ABOVE the statement — a pump or hotel hold that settled lower — and drops the amount test entirely, so merchant identity carries the whole proof (similarity ≥ 0.9, unique in window, or ambiguous). As the amount test weakens down the table the other gates tighten. Holds are proposals like tolerant matches: excluded from coverage, never flipping a wallet event, settled by the user via resolveProposedMatch. Not covered: the $1.00 verification probe, whose capture bears no relation to the settled amount.
- 2026-08-17 — Statement reconciliation filters candidates to the card's billing currency (storage default CAD, matching walletNormalization/purchaseMerge). A foreign-currency observation is a different number for the same purchase, so USD 45.00 against a CAD 58.50 line was matching as a $13.50 tip — and the merchant gate is no defence there, because the merchant genuinely matches. Foreign purchases are now honestly unmatched; converting via the FX engine instead would need its own narrow FX-drift band, since issuer rate + FX fee drift lands inside the 25% tip band.
- 2026-08-17 — Merchant alias curation is user-editable at /settings/merchants (inline rename + category); a rename backfills Purchase.merchant and WalletEvent.merchantNormalized across all users sharing the rawString (accepted for beta per global-table posture).
- 2026-08-17 — Statement matching is tip-tolerant one-sidedly: a line may match a candidate 0–25% BELOW it (tips and settled pre-auths only add), status `matched-tolerant`, unique-in-window or ambiguous, and gated on merchant similarity ≥ 0.5 since the amount no longer identifies it. Exact matches resolve first across the whole upload so a tipped line never eats a capture some other line matches to the cent. Tolerant matches persist their candidate link but are excluded from coverage and MUST NOT flip a wallet event to RECONCILED; the user confirms or rejects each one, and that decision outranks the engine on later re-uploads. The wallet↔email matcher stays exact.
- 2026-08-17 — The two matchers keep separate merchant logic; `merchantsCompatible` is NOT lifted into the statement engine. Sharing it would lose alias resolution on the noisiest text in the system to remove a four-line function. Same relation, deliberately different resolution.
