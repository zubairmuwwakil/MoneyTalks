- 2026-08-27 — **The nightly valuation must warm the market-data cache before it reads it, and every non-fresh quote must say why it is not fresh.** For weeks the 02:00 UTC price cron recorded PARTIAL snapshots with 0/N holdings priced, and the only working repair was the owner clicking "Refresh Prices & Capture" by hand each morning. Evidence: every snapshot whose sole writer was the cron was PARTIAL; every COMPLETE one had a later manual `updatedAt`. **Root cause, in MarketLens, not here.** MarketLens answers from a cache and fans out to Yahoo only when the cache cannot answer; that fan-out ran under a hardcoded `fan-out-deadline: 8s`, and a *measured* four-symbol fan-out took **7.74 s on an already-warm instance** (cache-hit baseline ~205 ms, so ~7.5 s of it was the fan-out). At 02:00 UTC on a just-woken free-plan container it never finished, `invokeAll` cancelled the batch, and `buildQuote` served the cached candle — **byte-identical to a candle served because the market genuinely has no newer close**. That ambiguity is what hid it: there was no error anywhere, at either end. Rulings: (1) **A quote now carries a machine-readable cause** — `provider_deadline_exceeded`, `provider_error`, `budget_exhausted`, `session_in_progress`, `no_provider`, `no_data` — because "we could not reach the provider" and "there is nothing newer to have" are different facts and only one is an outage. (2) **Deadlines are sized for a cold start (45 s, env-overridable), not for interactive latency**; a background sweep that gives up early does not return faster, it returns worse data. (3) **`@Scheduled` is not a scheduler on a host that spins down** — MarketLens' 22:30 UTC warm sweep had never run in production, because a sleeping container fires no timers. The sweep is now driven over HTTP (`POST /api/v1/admin/quote-sweep`, 503 when it warms nothing) instead of a timer. **Consumers do not use that endpoint**: `/api/v1/admin/**` is `hasRole("ADMIN")` and In Unity holds a USER key, so a first cut that pointed the warm-up there would have 403'd every night — caught by probing the deployed service before shipping. A consumer warms *its own* symbols with `refresh=true` on the ordinary quotes endpoint (`warmQuoteCache`), which is a consumer operation needing no elevated role; the ADMIN sweep stays ADMIN because it spends shared provider budget across the whole demand set. In Unity's warm-up runs at **01:45 UTC**, 15 minutes ahead of the price cron, which repeats it as a backstop. (4) **The sweep force-refreshes, ignoring the cache.** The cache-miss test is `cachedTradeDate.isBefore(expectedSession)`, so a cache holding a *wrong* candle for the *right* date could never repair itself; a sweep that defers to the cache is a no-op in precisely the case that needs it. (5) **An in-progress session is not a close.** Yahoo's daily series includes the session currently trading, so any page view during market hours cached an intraday price *as that day's close* — and, being dated today, it could never be re-fetched today. Candles after `expectedSession` are now discarded (a no-op for crypto by construction, since its expected session is the current UTC day). (6) **In Unity validates `tradeDate >= expectedSession`, not `===`.** Exact equality made a validated price depend on two independently-deployed services agreeing on a calendar date; when they disagreed the whole account silently went PARTIAL. (7) **Warm-ups ping the slow path, never a health endpoint** — `/actuator/health` proved the HTTP layer was awake and nothing about the fan-out, which is the only part that costs anything. Two bugs found by the new diagnostics on their first run and fixed here: `QuotaService.ensureTodayRow` used Postgres `ON CONFLICT` against H2, so **every quota consumption in the demo profile threw and was swallowed** (`DatabaseDialect` is now public and applied there, as in the other two upsert repositories); and TSX holdings carrying `priceCurrency: "USD"` from the retired Alpha Vantage path are inflated ~39% by FX conversion (`xeqt.to` shows $636.77 instead of $458.90) — live rows self-heal on the next successful refresh, historical snapshots do not and are a separate repair.
- 2026-08-27 — **The catalogue can now hold a card that is not Canadian — this is capability, not authorization to ship a US market.** Catalogue 2.0/2.1 changes the shape every consumer reads. **What was wrong:** a fee, a credit and an earn rate were bare numbers that every caller silently read as CAD. That is invisible while all 41 cards are Canadian and wrong the moment one is not — the identical class of bug as `price_candle` shipping without a currency column (2026-08-18), and it is worth noticing that this repo has now made the same mistake twice in two different domains. **Shape:** `fee`/`credits` values become Money (`{amount, currency}`); every card carries `market` (`CA | US`) and `billingCurrency`; `earn.pointsPerUnit` replaces `pointsPerCad`; caps gain `calendarQuarter`. `Scorer` computes earn and the FX gate against the card's *own* billing currency, and the new `reportingCurrency.ts` converts to the CAD reporting figure **only at display and aggregation points** — a card's value is computed where it is denominated and converted once, at the edge, rather than at every arithmetic step. **`status: draft | published` is added** so the catalogue can hold a research-grade record that has not cleared D3's issuer-confirmed sourcing bar: `RecommendationEngine.recommend` and `PortfolioAnalyzer` refuse a `draft` card even if it appears in `ownedCardIds`, so a draft can never produce a checkout pick or a keep/cancel number, while the add-card and compare surfaces MAY show one clearly labelled. Promoting draft → published is a **data edit** (re-verify against the issuer, flip the field), never an engine change. **Four bugs the review caught, all downstream of the shape change and none of which a passing golden fixture would have surfaced:** `Scorer` valued a USD-billing card's cashback as if $1 USD == $1 CAD, and the twin's own new assertions had masked it with a `cadPerDollar` of 1.0; `capPeriodKey` had no `calendarQuarter` branch at all, so every quarterly-cap transaction was skipped as not-accruable forever and the bonus rate looked permanently available; `resolveCapAccrualOutcome` stored a raw CAD minor amount against a USD-denominated limit; and `ownerStateInput`'s `.strict()` schema had no `market` key, so setting it returned HTTP 400 — the field had a type but no persistence path. The Discover-only wallet gap in the default `acceptedNetworks` fallback was fixed here and in the Swift and Kotlin engines. **The line to hold:** `Market = 'CA' | 'US'` is a union member and a test fixture. The catalogue is 41 cards, **all `market: "CA"`, zero US**, in both this repo and PickMe; `status` is in the schema and **no card carries it**. A US market is named nowhere in the decision record or in ECOSYSTEM's horizon, so shipping one is new scope that needs a ruling — this entry exists so that the code is not later mistaken for that ruling (ECOSYSTEM: "existing code is NOT authorization"). Expansion also remains **demand-driven** under D3, via `/cards/request` → `/admin/card-requests` → `catalogueRequestPr.ts`, which opens a sourcing *brief* against PickMe and deliberately authors no card data; batch-ingesting a market is the opposite policy and would supersede D3, not implement it.

Ids are now catalogue tokens, labels stay presentation, and `categories.test.ts` derives its expectation from the vendored catalogue — a scorable category with no picker entry fails CI, because that failure is otherwise silent. Legacy ids are kept **forever**, not until the migration runs (bookmarked URLs, future imports). (2) **PickMe already had the only merchant→category table in the ecosystem** and it was invisible to the hub: `CanadianMerchantPreIndex.swift`, ~150 rows of brand + category + MCC + accepted networks, editorial research rather than observed network data. The hub's problem is genuinely harder (a string, not a place), but it had three unused signals: `EmailTransaction.fromEmail`, `WalletEvent.latitude/longitude` (captured and stored since the native capture work, still unread), and the catalogue's own 39 referenced MCCs. **Geo is still unused** — a server-side reverse geocode is an external dependency, and the honest owner of that lookup is the device. (4) **The design is a ladder, not a keyword engine.** Keyword matching on raw strings is what produces confident nonsense ("CAFE" inside "CAFE SUPPLY WHOLESALE", "esso" inside "espresso"); the primitive is `normalizeMerchant` → brand key → exact whole-word lookup, with fuzzy evidence demoted to a suggestion. Seven tiers, one return shape carrying its `source`: userOverride/merchantAlias (certain) → observedMcc/emailDomain/brandPack (high) → processorPrior (medium) → none. **Only certain and high are written**; weaker readings surface as a one-tap ✨ pill so a guess never enters the spine wearing the same clothes as a fact. Carrying the source is what buys the provenance chip, re-runnability when the pack ships rows, and an LLM tier later as one more `case` with no call-site change. (5) **Two silent bugs fell out of the wiring.** The wallet-events route hardcoded `category: "unknown"` with a comment saying the category was not knowable, while `merchantAlias` — fetched 80 lines above — was in scope carrying one: every at-till verdict was computed at base earn. And `gmailReceiptProcessing` never set a category at all, while its accrual gate requires one, so **every Gmail-sourced purchase was excluded from the cap ledger outright**, not merely mis-scored. (6) **A pack row was wrong upstream and was fixed upstream:** all four Canadian pharmacy chains sat at `other` while six catalogue rules score `drugStore` — three of them (`pc-we-shoppers-45pts`, `pc-world-shoppers-35pts`, `pc-mc-shoppers-25pts`) firing specifically at Shoppers. Relatedly, `CATEGORY_BY_MCC` requires the pack to be **unanimous** about a code rather than modal: 5814 is 14 dining rows against 3 food-delivery, and a majority vote would call every Uber Eats order dining. (8) **Deliberately NOT done:** `MerchantAlias` stays global and any signed-in user still sets a category for every user — the 2026-08-17 ruling below ratified that posture for beta, and with signup open it is worth **revisiting as its own decision**, not quietly averaging. The resolver's tier-1 `userOverride` seam exists and has no writer today. - 2026-08-19 — **`PUT /api/spine/owner-state` is a MERGE, not a replace, and `GET` now exists.** The endpoint used to `upsert` `stateData` wholesale, which is last-writer-wins with no conflict detection: correct for one writer, silently lossy for two. PickMe writes its whole wallet on every setup save (`CheckoutFlowView`), so a card set or condition answer authored on the web vanished the next time the phone saved. `reconcileOwnedCards` already protected `ownedCardIds` with an additive union; the object around it had no such protection. Ratified policy, now enforced in `mergeOwnerState`: **`ownedCardIds` union — never remove, because a writer that cannot see a card is not evidence the card was sold**; `cardStates` merged per CARD not per field, so a card the writer never mentioned keeps its stored answers while a card it did mention is replaced entirely (which is what makes un-ticking an answer still work); `switchThreshold`/`valuationsCad`/`carry`/`ownerStateVersion` last-writer-wins, because averaging two whole-object preferences produces a third setting neither client asked for; `defaultCardId` never left dangling. Concurrency reuses the optimistic `updateMany`-guarded-on-`updatedAt` pattern from `reconcileOwnedCards`, but with a bounded retry and a **409 rather than a false success** — that function converges on the next read because it is idempotent, whereas this one is carrying a user's edit. `GET` returns `ensureOwnerStateRecord`, with `ownerState: null` a real answer (no catalogue-linked cards yet), never an error.
